## The gap in detail

`scripts/bulk_export_for_flythrough.py` calls:

```
dotnet run --project src/RiftAssetDumper --no-build -- \
  decode-nif-geometry --id <hash> --mesh-block 0 --export-obj --root <live>
```

The C# `decode-nif-geometry` command validates that the requested mesh-block exists in the NIF.
For the 10 test NIFs, block 0 is not a NiMesh — it's typically the root NiNode or a header.
The actual primary NiMesh is at block 6, 7, 27, or similar (varies per NIF).

The inventory `nif-mesh-binding-inventory.json` has:

- `MeshBlocks: int` (just a count, not a per-asset mapping) ❌
- No per-row `MeshBlockIndex` field ❌

The existing `probe-meshsize-lookup.json` (used by `batch_export_pos_only.py`) DOES have
per-asset mesh-block info, but it's not wired into FT-2.2's input.

## 5. Resume options (pick one)

### Option A — Add FT-2.0.5 (mesh-block discovery)

Insert a pre-FT-2.3 step that runs `probe-nif-mesh` for each candidate ID and writes
`Assets/build/flythrough/mesh-block-lookup.json`. Then modify the script to read the
lookup before each decode. Most surgical, but adds 1-2 hours of work.

### Option B — Iterate mesh blocks per NIF

Modify `bulk_export_for_flythrough.py` to probe all mesh blocks (0..N) per NIF and pick the
first that succeeds. Slower (N×M attempts) but no separate discovery pass.

### Option C — Reuse existing `probe-meshsize-lookup.json`

Extend `load_asset_ids_from_inventory` to also return `(asset_id, mesh_block)` tuples
from the existing `Exports/probe-meshsize-lookup.json` file. Fastest fix, but couples
FT-2.2 to an existing artifact (which the plan didn't anticipate).

**Recommended**: Option C (reuse existing lookup) — it's the fastest path and reuses
already-proven data. Fall back to Option A if the lookup doesn't cover the 10 test NIFs.
